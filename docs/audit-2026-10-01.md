### A01 — the alleged target-terrain adjustment is an AI branch

Locations: [firing.ts](../src/engine/firing.ts), lines 88–100; [firingHelpers.ts](../src/planner/firingHelpers.ts), approximately lines 241–256; [spec.md](spec.md), live-fire formula; [reverse-engineering.md](reverse-engineering.md), record field `+0x2E` and §7b.

The engine substitutes `+2` for rough terrain, `-1` for bush and `-3` for low wall. The planner duplicates this interpretation. The binary does something different:

1. At `seg6:3719`, the hit routine locks the shooting robot and follows its first word to the parent Team record.
2. `seg69:07A8` tests whether that Team's field `+0x2E` is nonzero. Zero selects the human path at `seg6:3790`.
3. The nonzero branch at `seg6:374F–3783` selects special additions for field values 1, 2 and 3.
4. The setup UI at `seg17:2B68–2BA8` uses this same Team field to select string resource `329 + field`. The resources are Human, Stupid, Ferocious, Crafty, Paranoid and Home Only.

This is a player/AI-type field, not the terrain under the target. In the audited executable, the special additions are field 1: `-3`, field 2: `+2`, field 3: `-1`. RoboArena v1 consists of human players, so these substitutions should not enter its human hit-score formula.

**Impact:** human combat probabilities vary with terrain for the wrong reason, and the planner consistently explains the same incorrect formula. Legitimate terrain effects through cover and sight remain relevant.

**Action:** correct the record annotation and formula provenance, then update engine, planner, spec, explanations and focused tests together. This finding is CONFIRMED by static data flow in the inspected Windows executable. A short original-game qualitative check would be useful corroboration; existing broad test counts are not corroboration of this interpretation.

### A02 — the human addition depends on selected Scan distance

Locations: [constants.ts](../src/engine/constants.ts), line 99; [catalogData.ts](../src/engine/catalogData.ts), lines 17–36; [firing.ts](../src/engine/firing.ts), lines 96–100; [firingHelpers.ts](../src/planner/firingHelpers.ts), accuracy-index calculation.

The clone treats the table at DGROUP `0x1596` as eight weapon/command additions. The actual human branch at `seg6:3790` indexes it using argument `[bp+0x0C]`:

- Aim at `seg6:1E76–1E90` passes **zero** for that argument, separately from the weapon selector. Human Aim therefore takes table entry zero, `+4`, for each direct-fire weapon.
- Scan at `seg6:2075–2093` passes local `[bp-0x0A]`. The command decoder `seg13:060E` reads this from command byte `+9`. The same value is passed to acquisition routine `seg18:072C`, where the comparison at `seg18:084F` uses it as the **maximum target distance**.

The complete signed table for indices 0–18 is:

```text
4, 7, 6, 5, 4, 3, 2, 1, 0, 0, -1, -1, -2, -2, -3, -3, -4, -5, -6
```

**Concrete difference:** human Rifle Scan with selected maximum distance 18, actual target distance 13, cover class 4, clear sight, no stagger and no off-tile penalty has binary-derived score `18 - 1 - 6 = 11`, giving `112/256 = 43.75%`. The current clone adds `+7`, clamps score 24 to 19, and gives `240/256 = 93.75%`. For human Machine Gun Aim at distance 13 and cover class 3, the same trace yields score 14 (62.5%); the clone yields 12 (50%). These are calculations from the inspected binary, not measured firing samples.

**Action:** carry selected scan maximum distance into the score inputs; replace the weapon-index mapping with the confirmed human mapping; cover range endpoints and all direct-fire weapons with independently specified expectations. Preserve sight-strength penalties as a separate factor. Do not infer an additional numeric target-speed modifier from this finding.

Both A01 and A02 change replay outcomes. Plan an explicit rules-version/compatibility decision before updating golden fixtures or loading persisted matches with corrected rules. The current replay format version alone does not provide an old-engine implementation.

### A03 — visible scanners disclose hidden third-party robots

Location: [server/view.ts](../server/view.ts), lines 65–77. The user-facing inspector consumes the resulting events in [events.ts](../src/lib/explain/events.ts).

The projection authorizes `scan-target-acquired` solely by `shooterId`, then passes `targetId` and exact distance through. `fired` also carries the exact aimed coordinate when only the shooter is authorized.

Reproduction: observer A at `(1,1)` faces north; visible enemy B at `(6,1)` faces south; enemy C at `(6,3)` is behind A's visibility gate. A's initial projection contains only A and B. After B scans, A receives:

```json
{"kind":"scan-target-acquired","shooterId":"b","targetId":"c","distance":2}
{"kind":"fired","shooterId":"b","target":{"x":6,"y":3},"fireMode":"scan"}
```

**Impact:** in a three- or four-player match, watching a visible opponent reveals another opponent's hidden identity and position. This is accessible in ordinary projected events, including event inspection/export.

**Action:** authorize each disclosed identity and coordinate, not only the event's actor. An observed enemy's private acquisition result should not become the observer's contact intelligence. Define which visible shot/projectile observations are legitimate and redact or project them accordingly. Add three- and four-player tests that vary an unauthorized robot's state and verify the observer receives no unauthorized change.

### A04 — conditional ammunition makes accepted combined orders invalid

Locations: [server/matches.ts](../server/matches.ts), lines 131–160 and 222–228; [server/rooms.ts](../server/rooms.ts), lines 384–389.

Order validation runs `resolveTurn` with just one participant's orders against the current complete state. This does not prove those orders remain valid when the other participants move and fire.

Reproduction: a Missile robot has one missile left. It programs one second of Scan with maximum distance 5, followed by Aim. An opponent starts at distance 6 and programs movement into range. Each player's order set validates separately. In the combined turn, Scan acquires the moving opponent and spends the missile; the following Aim fails with `Aim & Fire requires available ammo.`

After failure the match has `phase: resolving`, both participants locked, and a pending resolution. The room service saves the seed and combined orders **before** calling the resolver. The persistence/recovery path therefore retries the same invalid input; ordinary reconnect or service restart does not repair it. The focused probe demonstrates the engine/lifecycle failure; the restart consequence follows from this persistence path rather than a newly executed crash test.

**Action:** implement authoritative structural/state validation with conservative conditional resource accounting, independent of speculative enemy actions. Ensure every accepted combination has a defined resolution outcome, and provide a durable recovery state for unexpected resolver errors. Add an integration regression through lock, persisted failure and reopen. Planner-side restrictions do not protect the server boundary.

### A05 — a defeated player can hold the remaining players indefinitely

Location: [server/matches.ts](../server/matches.ts), lines 55–57 and 211.

`activePlayerIds` excludes resignations, but includes players whose entire Team is destroyed. In a three-player probe with A and B alive and C at zero HP, A and B lock orders and the match stays in planning because C is still counted.

**Impact:** a player who leaves after losing can block the remaining Survival match unless they explicitly resign. Requiring a defeated participant to continue acknowledging and submitting empty turns is an avoidable liveness dependency.

**Action:** derive resolution participants from authoritative surviving, non-resigned teams. Let eliminated participants independently watch their available movies and results without gating survivors. Test elimination with three players, simultaneous eliminations, reconnect and resignation interactions. Never infer elimination from an opponent's visibility-filtered robot list.

### A06 — successful Save to server is presented as a conflict

Locations: [MatchGate.tsx](../src/components/setup/MatchGate.tsx), lines 189–219; [PlannerExperience.tsx](../src/components/planner/PlannerExperience.tsx), lines 301–310; [state.ts](../src/planner/state.ts), lines 51–64.

Browser reproduction: deploy a robot, click Save to server, and receive the successful new revision. The planner remains dirty, treats its own acknowledged revision as an external update, and shows: “The server state changed while this browser has an unsent draft. Your work was preserved.” It offers Keep local draft / Use server turn despite the successful save.

**Action:** distinguish acknowledgement of a submitted payload from an unrelated authoritative refresh. Clear dirty state only when that payload still matches the current draft; preserve edits made while a save was in flight. Test both cases and a real competing-tab conflict.

Screenshot: [false-save-conflict.png](../test-results/audit-2026-10-01/false-save-conflict.png). Screenshots remain local ignored audit artifacts.

### A07 — idle waiting continuously grows the database

Locations: [MatchGate.tsx](../src/components/setup/MatchGate.tsx), lines 139–145; [server/index.ts](../server/index.ts), lines 251–256; [server/storage.ts](../server/storage.ts), lines 93–115.

A waiting client polls every 2.5 seconds with fresh request IDs. Each `GetMatchState` response is inserted into `request_results` as a complete snapshot, with no expiry or bound. It persists duplicate read results even when gameplay has not changed.

The disposable audit room's sampled match snapshots averaged approximately 17.4 KB. At that size, 34,560 polls per continuously waiting client per day imply roughly **600 MB/day of JSON payload alone**. This is an extrapolation, not a 24-hour load measurement; SQLite overhead and longer match history can increase storage further.

**Action:** stop permanently caching read-only snapshots. Keep bounded mutation-idempotency records separate from durable room/turn history, and specify retention semantics compatible with delayed retries and rejoining. Confirm stable storage size while an unchanged room is polled repeatedly.

The audit also reports critical Next.js image-processing advisories. Other findings have lower demonstrated exposure in this application. Update the remaining affected packages within supported dependency ranges and confirm `sharp` is at least 0.35.4 for its [libheif advisory](https://github.com/lovell/sharp/security/advisories/GHSA-rgj7-g3m4-5g8c). ## Improvements and follow-up investigation

**Incremental replay recording.** `resolvePendingTurn` first resolves the new turn, then `createReplayLog` replays the entire history, then `verifyReplay` replays that history again synchronously. This makes per-turn work grow with match length and total work quadratic in turn count; it also occupies the shared Node event loop. Record the latest result and digest incrementally, keep full verification as an explicit audit path, and benchmark representative long matches before deciding the performance change's release priority. This audit did not establish a supported-device performance failure.

**Movie layout at the minimum viewport.** At 1024×768 in the desktop browser, the page's 1024-pixel minimum body width exceeds its 1009-pixel client width after the vertical scrollbar appears. The 24×24 movie board is 672 pixels high and begins around y=184; playback controls begin around y=872. The resulting page is 1,451 pixels high, with a 15-pixel horizontal overflow and controls below the initial screen. Consider a viewport-sized movie frame, fit-to-view default and persistent transport controls, and fix the body width floor's scrollbar interaction. Validate touch/pan/zoom on a physical iPad rather than treating viewport emulation as Safari evidence. Screenshot: [movie-landscape.png](../test-results/audit-2026-10-01/movie-landscape.png).

**Planner camera context.** The follow-up 1280×900 browser check found the selected robot at `(0,0)` outside the initial centered, fit-width view, including after a next-turn planner mount. Zooming out to 42% revealed the correctly rendered robot. This is the current deliberate cropping policy, not a failed SVG decode. Consider initially framing the player's home area and keeping the selected robot visible; focusing the board and pressing Enter currently permits deployment at the offscreen keyboard tile before any arrow key triggers auto-pan. Review this alongside the movie camera improvements.

**Evidence quality.** The existing RE verifier accurately detects changes to the recorded bytes/tables, but it passes while A01 and A02 are semantically wrong. Add argument provenance and record-identity evidence to important binary claims. For new combat expectations, use hand-traced binary inputs or small empirical observations independent of the implementation. Avoid tests that only compare the planner against the same incorrect engine formula.

**Compatibility and storage clarity.** Document how changed engine rules interact with durable pending turns and existing replays. The SQLite `locked_orders` API/table also exists alongside the actual live path, which persists locks in the room JSON; clarify or consolidate that duplication during the planned storage migration. Do not mistake tests of the separate table for proof that the live path uses it.

## Recommended work sequence

**First, patch dependency finding A08 before exposing the Windows server for further network testing.** Keep this update separate from game-rule changes so regressions are attributable. Then proceed with the gameplay and service cleanup below.

1. **Close the server trust and liveness gaps.** Add focused regressions for A03–A05, fix projection and authoritative order validation, and verify failures/rejoins through the actual durable service boundary. Acceptance: hidden third-party state remains private, every accepted combined program resolves, and eliminated seats cannot stall survivors.
2. **Correct the two combat interpretations together.** Preserve the binary trace, perform a small targeted original-game check if available, and update spec, constants/catalog/types, resolver, planner explanations and tests as one coordinated change. Establish replay/rules compatibility before refreshing fixtures.
3. **Repair routine play.** Fix save acknowledgement and polling retention. Check that repeated save/reload behaves predictably and waiting does not accumulate duplicate snapshots indefinitely. Address the demonstrated minimum-viewport overflow within the bounded presentation scope.
4. **Complete Phase 12.2 with actual evidence.** Run the planned four-session match, restart points, independent playback, keyboard regression and physical iPad Safari match on the corrected candidate. The smoke test in this audit does not close these gates.
5. **Then perform Phase 12.5.** Migrate authority to the planned Vercel HTTP/Supabase architecture after the local candidate is frozen. Carry privacy, idempotency and resolution regressions into the new transport, then execute the deployed two-network gate.

For later improvements, prioritize understandable combat feedback, fit-to-view movie controls, and measured long-match efficiency. Keep new sports, AI, alliances and Stealth gameplay within their scheduled phases. The most valuable immediate work is correctness and confidence, not a framework rewrite or feature expansion.
